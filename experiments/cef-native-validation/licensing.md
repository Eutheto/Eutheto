# CEF 154 licensing and security-update gate

**Prepared:** 2026-10-06 · **Scope:** the four pinned CEF 154.0.34 minimal SDK archives in [`pins.json`](pins.json), their cached notices at `/home/zeb/code/eutheto/.cache/cef-review-154.0.34.FyYeH0`, and this experiment's synthetic font fixture. This is a distribution gate, not legal advice or authorization to integrate, publish, or redistribute CEF.

## Decision

**NO-GO for redistributing the CEF SDK/runtime or production adoption.** The CEF/Chromium BSD notices are identifiable and the exact cached SDK notices were checked, but FFmpeg's exact license composition and corresponding-source/rebuild evidence are not closed. The files below do not establish GPL-enabled FFmpeg, nonfree FFmpeg, or their absence. The experiment has no public-artifact authorization; its generated PDFs remain private. Rendering a PDF with CEF does not automatically make the PDF subject to CEF/Chromium or FFmpeg's software license; embedded font/data terms are separate and were not audited.

No separate `licensing.json` is added: [`pins.json`](pins.json) already owns the four machine-readable archive hashes, and a second manifest would duplicate them. Notice-file hashes and their dispositions are recorded here.

## Component-specific obligations and exact unknowns

### FFmpeg — LGPL 2.1-or-later unless GPL-only code was enabled

All four actual cached `CREDITS.html` files include FFmpeg's license statement: most FFmpeg files are LGPL-2.1-or-later, with some MIT/BSD-style files; optional GPL-2-or-later parts change FFmpeg's license if enabled. That credit is a license inventory, **not** the release builder's configuration or proof of clearance.

Pinned Chromium source evidence makes FFmpeg an expected media component, not merely a credit: [`media/media_options.gni`](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/media/media_options.gni) defaults `media_use_ffmpeg = true` (for Blink builds), and [`media/ffmpeg/BUILD.gn`](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/media/ffmpeg/BUILD.gn) builds an FFmpeg source set into `//media` via `//third_party/ffmpeg`. Chromium's pinned [`DEPS`](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/DEPS) pins the FFmpeg source mirror revision to `a06d51a20a28f980b2ddc6b7d73d69b2d29bf323`. CEF's pinned [`tools/gn_args.py`](https://raw.githubusercontent.com/chromiumembedded/cef/14c5a089e8452874cb1a556dc3fde26ed2d87723/tools/gn_args.py) accepts builder-supplied `GN_DEFINES`; the cached README/source commits do not disclose the actual per-archive GN arguments. Thus LGPL FFmpeg is the conservative distribution assumption for each target, but exact inclusion/configuration is **conditional on the release build settings**.

The CEF READMEs and CMake binary lists identify the `libcef` shared object/DLL/framework, not a separate FFmpeg shared library. They do not establish whether FFmpeg is incorporated in `libcef` or how a recipient can rebuild or replace the relevant library. Do not assume a stand-alone FFmpeg library can be replaced directly.

Minimum LGPL-2.1 distribution path if FFmpeg is present: provide its exact corresponding source (including the pinned `DEPS` revision and any applied patches), applicable license/notices, and the build/configuration scripts needed for a recipient to modify and rebuild or replace the relevant library. If FFmpeg is part of `libcef`, rebuilding/replacing `libcef` may be the applicable route. Whether that, or additional object code/relinking or installation information, is required depends on the actual combination; assess it against [LGPL-2.1 §6](https://www.gnu.org/licenses/old-licenses/lgpl-2.1.html#section6) and the exact linkage. Do not make a separate FFmpeg library or direct replacement without rebuilding `libcef` a prerequisite. FFmpeg's [maintainer compliance guidance](https://ffmpeg.org/legal.html) recommends dynamic linking and matching source/build instructions; the license text governs the available compliance route.

The CREDITS page says GPL-only FFmpeg parts are optional and that enabling them changes FFmpeg to GPL-2-or-later. The exact binary flags/branding, GPL-only object inclusion, and any `nonfree` configuration are **unknown for all four targets**. No claim that GPL was enabled—or disabled—is made. If GPL-only code was included, a GPL review is required; if a nonfree FFmpeg build was used, its own notice says the resulting binary is non-redistributable. Either finding blocks the current proposed distribution path.

### liblouis — LGPL 3-or-later credit, not in these minimal runtime payloads

Every target's cached CREDITS page contains the Braille Translation Library notice, copied from the liblouis header and stating LGPL version 3 or later. The pinned Chromium [`README.chromium`](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/third_party/liblouis/README.chromium) calls it LGPL-3.0, `Security Critical: yes`, `Shipped: yes`, and a WebAssembly module with local wrapper/table changes. Its `src` gitlink points to liblouis commit [`9700847afb92cb35969bdfcbbfbbb74b9c7b3376`](https://github.com/liblouis/liblouis/tree/9700847afb92cb35969bdfcbbfbbb74b9c7b3376). That upstream Chromium record is for Chromium's ChromeVox use, not proof that CEF's SDK includes the component.

At the pinned source, [`third_party/liblouis/BUILD.gn`](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/third_party/liblouis/BUILD.gn) places its generated files under `resources/chromeos/accessibility/chromevox/third_party/liblouis`; [`liblouis_library.gni`](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/third_party/liblouis/liblouis_library.gni) emits the WASM, JS wrapper, data and tables as separate files. The pinned CEF [`make_distrib.py`](https://raw.githubusercontent.com/chromiumembedded/cef/14c5a089e8452874cb1a556dc3fde26ed2d87723/tools/make_distrib.py) copies a fixed runtime-resource list (`chrome_100_percent.pak`, `chrome_200_percent.pak`, `resources.pak`, `icudtl.dat`, locales), not that ChromeVox resource directory; the pinned CEF [`BUILD.gn`](https://raw.githubusercontent.com/chromiumembedded/cef/14c5a089e8452874cb1a556dc3fde26ed2d87723/BUILD.gn) has no `liblouis`/`chromevox` references.

The exact four archives were also inspected without executing SDK code: none has a member path containing `liblouis`; each target's `resources.pak` was parsed using the pinned Chromium [`DataPack` format reader](https://raw.githubusercontent.com/chromium/chromium/b859317bf11f6be47f9b7799ec690a0a42a1fb33/ui/base/resource/data_pack.cc), including its whole-file GZIP handling. All are format v5. The resource payload census found no `liblouis`, `chromevox`, wrapper/export-name, or WebAssembly-magic matches: Linux has 5,602 resources, Windows 5,632, and each Mac archive 5,282. Together with the separate ChromeVox output path and CEF's package whitelist, this establishes that liblouis is not in these four minimal SDK runtime payloads. Its CREDITS entry is a broad credit, not evidence of a distributed liblouis binary; **no LGPL-3 source/relink obligation for liblouis is triggered by these SDK runtime payloads**. Keep the supplied CREDITS unchanged.

### Fixture fonts and generated PDF

[`fixture.html`](fixture.html) uses only CSS `font: 14px sans-serif`; it has no font files, `@font-face`, remote stylesheet/font, or external font dependency. Its CSP explicitly sets `font-src 'none'`. This fixture bundles no font software; rendering falls back to host system fonts (Linux setup expects system fonts). The OFL text in CREDITS does not show that a particular credited font is embedded in the fixture or SDK. A rendered PDF is not automatically covered by CEF/Chromium's code licenses merely because CEF produced it; any embedded font/data terms are separate. The experiment keeps PDFs private, and actual PDF font embedding/OS-font terms were not audited. Any future public PDF or bundled-font use needs a separate check of the exact embedded font files and terms.

## CEF maintenance/security-update disposition

The [maintained CEF branches/building policy](https://chromiumembedded.github.io/cef/branches_and_building.html#current-release-branches-supported) currently lists Chromium M154 / branch 8037 as **Stable** (last refresh shown as 2026-10-05) and M152 as **Extended**. It says ordinary stable branches receive broad security fixes for roughly two weeks after entering stable; every fourth even milestone starting at M152 receives roughly eight weeks total on Extended. M154 is not an Extended branch. The [CEF channel-change issue](https://github.com/chromiumembedded/cef/issues/4114) records the even-milestone policy and later Extended builds. CEF also says branch updates are manual and may lag Chromium announcements. These are maintained policy windows, not a security SLA or an automatic update channel.

**Status:** the October 05 M154 archive is on the currently supported Stable branch, but its security window is short and the pin will not update itself. No exact support end date is inferred. Before any future product use, re-check the live branch table and current CEF/Chromium security revisions, replace the pin through a newly reviewed artifact, and repeat this licensing gate. An unchanged source commit or old stable label is not a security-update plan.
