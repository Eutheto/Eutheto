# Linux CEF sandbox evidence and policy gate

This is an experiment-only assessment for CEF `154.0.34+g14c5a08` / Chromium `154.0.8037.98`. The known Linux result is the existing `No usable sandbox!` refusal; it was not rerun here. The probe keeps `USE_SANDBOX=ON` and `CefSettings.no_sandbox=false`. That failure is not evidence that the SDK helper is absent, nor does helper presence prove the sandbox is usable.

## Read-only SDK evidence

The cached `linux64.tar.bz2` is the exact pinned archive (`sha256=e87e2c76304372dd28b899ceb6efa4b353f52700594ddc358a8237ec07ec6492`, matching `pins.json`). Its matching member is:

```
cef_binary_154.0.34+g14c5a08+chromium-154.0.8037.98_linux64_minimal/Release/chrome-sandbox
```

The tar header reports mode `0755`, uid:gid `11:9999`, size `31,680` bytes—not root-owned and not setuid. Streaming that member to `sha256sum` and `file` (without writing or executing it) gave SHA-256 `02deb82893f0fd892d9041f7f2dc109dc132ad0bf303cef946f9660bf98eb2e0` and an x86-64 ELF PIE with build ID `fe0874a9e7efce2bb6406071e205eab652b63c62`. The helper was not run or granted privilege.

The matching cached CEF `cmake/cef_variables.cmake` lists `chrome-sandbox` in `CEF_BINARY_FILES`; `USE_SANDBOX` defaults on and adds `CEF_USE_SANDBOX` when enabled. This is SDK inventory/build configuration, not proof of runtime sandbox availability. The experiment's `CMakeLists.txt` removes `chrome-sandbox` from that copy list. The admission code rejects archive mode bits outside `0777`, ignores archived ownership, and creates executable members as owner-only `0700`; it cannot install a root-owned setuid helper. Thus the helper is available in the pinned archive and safely admitted as an unprivileged file, but is not installed in the experiment runtime or usable as the setuid helper.

The cached archive is local and matches the pin; no provisioner inventory interface was needed. Keep CMake's helper exclusion and provisioner's owner/mode normalization: the scoped CI AppArmor path does not promote the archive helper. Setuid-helper packaging remains separately unauthorized pending administrator/security-owner approval.

## Sandbox choices

Chromium's pinned Linux sandbox overview describes selecting mechanisms based on kernel support and layering setuid, namespaces, and seccomp-BPF. CEF likewise documents Linux sandbox prerequisites as system-capability-dependent. These mechanisms are not interchangeable with disabling the sandbox.

| Choice                                                              | Security and packaging implications                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Authorization needed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Use only the unchanged host's user-namespace policy**             | Adds no privileged file, AppArmor exception, or global sysctl change. It works only if the host kernel and its existing policy already permit the required namespaces. Allowing user namespaces exposes kernel namespace-related interfaces to unprivileged processes. This is the only path that tests feasibility without changing host policy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | No new policy authorization if it already works. The known `No usable sandbox!` result remains a failure until a normal run succeeds. This investigation did not inspect workstation/CI policy values and does not diagnose the exact refusal.                                                                                                                                                                                                                                                                                                                             |
| **Temporary root-managed AppArmor profile in disposable Ubuntu CI** | Explicitly authorized for the scoped Linux matrix only, with `--linux-apparmor`; not for a workstation, production integration, or persistent package. Install refuses unless Ubuntu reports `apparmor_restrict_unprivileged_userns=1` and AppArmor is active. It changes neither value. The bounded installer copies only the known CEF runtime files and `locales/*.pak` from the user's `build/Release` into `/usr/lib/eutheto-cef-native-validation/<run>-<attempt>` as root-owned, non-writable runtime files; it omits `chrome-sandbox` and never executes CEF as root. The root-owned profile attaches only to that copied `cef-probe` and grants `userns`. Its `flags=(unconfined)` mean this is **not filesystem confinement**: it is a narrow exception to the host's unprivileged-userns restriction, not a claim that the application is otherwise sandboxed by AppArmor. Cleanup, after CEF settles, unloads/removes only the profile and root tree whose exclusive claim, token, and exact profile contents match. | The user authorized this temporary CI-only policy change. The workflow must use a trusted push checkout only (never untrusted PR code); it installs the policy script as root-owned `0555` under its exclusive root-owned `0755` tools directory before SDK/native code runs, then invokes that immutable copy using `/usr/bin/python3 -I -B`. Native CEF still runs as the unprivileged runner. This design does not claim that a passwordless-sudo hosted runner is safe against malicious same-UID native code; use only disposable runners without production secrets. |
| **Install this matching SDK helper as root-owned setuid**           | The cached helper is an ordinary `0755` file, not a ready-to-use setuid helper. Using the setuid path requires an administrator/package manager to install the exact CEF-matched helper at a stable, non-user-writable location, root-owned with the setuid bit (normally `root:root 4755`). That creates a privileged executable in the trusted computing base; updates must replace it only with the helper matching deployed CEF and preserve safe ownership/mode. Never set this mode in the SDK cache or work directory.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Not authorized. It needs separate administrator/security-owner and packaging approval to install, maintain, and remove a root-owned setuid executable. CMake continues to omit it.                                                                                                                                                                                                                                                                                                                                                                                         |

The runtime root follows the hosted image's filesystem permissions: the official [Ubuntu runner-image setup](https://github.com/actions/runner-images/blob/main/images/ubuntu/scripts/build/configure-system.sh#L13-L17) executes `chmod -R 777 /opt`, so the installer correctly rejects `/opt` as an unsafe root-owned ancestor. Runtime custody now uses `/usr/lib/eutheto-cef-native-validation`; every parent remains checked for root ownership and no group/other write permission, and install still fails closed if the actual target does not meet those checks.

The root tool requires sudo's nonzero `SUDO_UID`, copies only from a `build/Release` owned by that same user, and refuses direct-root invocation. Its root-only custody marker binds the installer token and invoking UID; a second marker binds the token to the exact profile contents. The root script itself is installed into a separate exclusive root-owned tools directory before any SDK/native code is run.

The profile file is `/etc/apparmor.d/eutheto-cef-native-validation-<run>-<attempt>`; its loaded label also carries the operation token.

The immutable root entrypoint is invoked as `sudo -n /usr/bin/python3 -I -B <root-owned-tools>/linux_policy.py install <absolute-build/Release> <numeric-run> <numeric-attempt> <32-lowercase-hex-token>`. Cleanup uses `sudo -n /usr/bin/python3 -I -B <root-owned-tools>/linux_policy.py cleanup <numeric-run> <numeric-attempt> <same-token>`. It emits only `installed`, `install_failed`, `cleaned`, `cleanup_failed`, or `invalid_request`.

The installer is bounded to 10,000 runtime members and 3 GiB copied. Its root operation has a 120-second deadline and up to 30 seconds for best-effort rollback (150 seconds total, within the supervisor's 180-second bound); cleanup is limited to 30 seconds (within the 60-second supervisor bound). Each `apparmor_parser` process is limited to 10 seconds, then its process group is killed and waited on briefly. A forced kill, kernel-uninterruptible process, or host teardown can still leave a root-owned tree or policy file; primary cleanup and runner disposal remain necessary. The runner's trusted `probe.py` compares hashes of the host executable, `libcef.so`, and `icudtl.dat` between source and installed copies before unprivileged execution and hides the original build/SDK runtime during those cases. This verifies copied-runtime use, not CEF sandbox success.
Primary reports the first candidate (`4cb72a7`, run `37553821340`) compiled the Linux SDK but stopped before invoking this installer; the route remained unchanged-userns, with no `toolFailed` or `build-failed`. No AppArmor profile was installed/loaded and no policy mutation occurred. Profile parser/load/remove behavior and actual user-namespace sandbox usability remain unverified.

No global user-namespace/AppArmor sysctl change, setuid-bit change, borrowed helper, no-sandbox fallback, workstation policy change, or production adoption is authorized. Linux feasibility remains unknown until the scoped native run settles and the normal CEF sandbox reports success; failure of this experiment is not permission to widen the policy.
